# 第 4 步 · 待补问清单（报价闸门）

> 产物: `.req/questions.md` ｜ 过关: `gate.mjs check 4` ｜ **不过不报价**

## 陪跑流程

1. 用 ① 把前三步里所有【需要确认】和「推断」转成问题，按三档排序。
2. 每题写"为什么要问"：答案不同，报价、范围或设计会怎么变。说不出来的题删掉。
3. 用户去问客户（电话、微信、二次拜访），答案回填，写清出处（谁、什么时候、什么渠道）。
4. 答案回填后，把对应产物里的【需要确认】改掉，**推断被推翻的要回改前面的产物**。
5. `gate check 4`。T1 有一题没答案，就不能进入报价。

## 三档口径

- T1 影响报价、范围、可行性：做不做某模块、用户量和数据量、要不要对接现有系统（ERP/MES/企微/钉钉）、数据能不能给、谁签字验收、预算区间、上线时间。
- T2 影响设计：字段、分支流程、权限粒度、界面形态、导出格式。
- T3 开发时再定：文案、默认值、颜色。

## Prompt ① 汇总问题

```
下面是目前的调研产物：
<<注入 .req/intake.md>>
<<注入 .req/stakeholders.md>>
<<注入 .req/process.md>>
把所有【需要确认】、所有「推断」、所有缺失的角色和材料，转成问题，填 .req/questions.md 的问题表：
1. 每题只问一件事，用客户听得懂的话，能用选择题就用选择题。
2. 档位按 T1/T2/T3 口径打，拿不准的往高档打。
3. "为什么要问"写清楚：答案不同，报价、范围或设计会怎么变。
4. "问谁"填具体角色。
按 T1 → T2 → T3 排序。最后告诉我：哪 3 个 T1 最该先问。
```

## Prompt ② 把问题发给客户

```
把 .req/questions.md 里尚未回答的 T1、T2 问题，改写成一条可以直接发给客户的微信消息：
开头一句说明用途（为了准确报价/避免返工），问题编号保留，T1 放前面，总长度不超过一屏。
```

## 判据

- 问题按风险收集，不设数量下限，不为凑数而问；至少 1 题 T1。一个 T1 都没有 = 没认真想，或者在硬猜。
- 所有 T1 的答案和出处都已填。
- 模判：每题的"为什么要问"是否真的会改变报价、范围或设计。

## 过关前自查

- 有没有问"预算区间"和"希望什么时候上线"？这两个不问，报价就是盲报。
- 有没有问"现在有哪些系统，要不要对接"？对接是工作量的最大变量。
