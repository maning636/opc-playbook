# 第 6 步 · 范围与验收

> 产物: `.req/scope.md` ｜ 过关: `gate.mjs check 6`

## 陪跑流程

1. 「报价内」列出这次要交付的需求编号和交付物。**报价只认这一页**。
2. 「不含」至少 3 条，从需求的「边界」、process 的「不碰的部分」、P2 里挑。写得越具体，验收时越少扯皮。
3. 每条 P0 至少写一个验收用例：操作步骤 + 可判定的期望结果 + 验收人（第 2 步的验收签字人或其指定人）。
4. 写变更规则：怎么提、几天内评估、怎么计价、谁决定。
5. `gate check 6`。通过后才能报价、签合同。

## Prompt ① 需求 → 范围与用例

```
基于需求：<<注入 .req/requirements.md>>
和角色：<<注入 .req/stakeholders.md>>
按 .req/scope.md 模板输出：
1. 报价内：全部 P0 + 你建议纳入的 P1，每条写交付物。
2. 不含：至少 3 条，优先写客户最可能默认"应该有"的东西（例如移动端、历史数据迁移、二次培训、对接其他系统）。
3. 验收用例：每条 P0 至少一个，期望结果照抄或细化需求里的验收句，验收人用拍板人。
4. 变更规则：给一个默认方案（例：书面提出，3 个工作日评估，按人天计价，客户项目负责人决定），标【需要确认】让我和客户确认。
```

## 判据

- 每条 P0 都出现在「报价内」，也都出现在验收用例表里。
- 「不含」≥3 条。
- 变更规则四项（提出方式、评估时限、计价方式、决定人）都已填。
- 第 4 步的 T1 已全部回答（门禁会连带检查）。
- 模判：「不含」是否覆盖了客户最可能误解的部分。

## 过关前自查

- 把「报价内」和「不含」念给客户的拍板人听，他会不会说"这个我以为是含的"？
