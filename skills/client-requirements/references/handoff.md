# H2 · 需求包交接契约

> 适用阶段：第 7 步机判与语义审核完成后，向工程层提交需求基线。
> 上游输入：`.req/` 七份产物。下游输出：engineering-standard 的需求追踪、架构与任务图。
> 通用信封遵循 agent-workspace-spec 09 篇；本文件只定义客户需求 payload。

## 1. 何时需要完整 H2

- 签约客户项目、需要报价与验收的项目：开发前必须形成并锁定 H2。
- 自有产品探索、一次性原型：不要求完整 H2，可先用 direction/VDF 和明确假设验证；进入多模块开发或正式交付时再补基线。
- 小修小补：沿用所在项目已有需求与变更流程，不重复建一套 PRD。

## 2. 通用信封

```yaml
schema_version: handoff/v1
artifact_version: REQ-2026-0001-H2-v1
business_id: REQ-2026-0001
producer: growth-ops/client-requirements
consumer: engineering-standard
status: submitted
source: .req/prd.md
hash: sha256:<由确定性工具计算>
created_at: <带时区的 ISO 8601>
```

需求 payload 使用 `requirement_schema: requirements/v1`。
`.req/` 是上游权威原件；工程层引用其来源与哈希，不维护可写副本。提交后内容变化必须产生新的 `artifact_version`。

## 3. 编号映射

项目内部可以沿用 F/A 短号，跨项目、跨库引用必须补全业务 ID。

| 上游字段 | H2 / 工程层 | 规则 |
|---|---|---|
| `P0` | `必须` | 缺了就不能验收，全部进入报价和追踪矩阵 |
| `P1` | `应该` | 本期计划做，未完成须在验收报告说明 |
| `P2` | `可以` | 有余力再做，不进入强制验收 |
| 出范围项 | `本期不做` | 保留在范围清单，不伪装成已实现需求 |
| `F03` | `REQ-2026-0001-F03` | 业务 ID 来自 `intake.md`，不重新分配 |
| `A01` + 需求列 `F03` | `F03-A01` | 用例归属于哪条需求，就嵌入该需求短号 |
| 上例跨库引用 | `REQ-2026-0001-F03-A01` | 补全业务 ID，不另起 A 序列 |

如果上游已经使用 `F03-A01`，不得再次拼接成 `F03-F03-A01`。
非功能需求只有进入本期验收和追踪时才分配 `N01/N02`；编号发出后不复用，来源仍指向原非功能条目。

## 4. 交接状态

```text
draft → submitted → accepted → baselined → superseded
```

- `draft`：七步进行中，可以包含问题和假设。
- `submitted`：第 7 步机判及 MODEL-CHECK 均完成，附来源与哈希。
- `accepted`：工程层确认需求可实现、验收可执行；不能测的条目退回，不直接替客户改。
- `baselined`：双方将该版本作为开发、变更和验收依据。
- `superseded`：被新 H2 版本替代，旧版本保留审计。

“工程层收到文件”不等于 accepted；`baselined` 之前不得把需求称为已锁定。

## 5. 正向与反向变化

### 商业需求变化（CP）

客户范围、费用、工期、验收或优先级变化时：

```text
提出 CP → 经营/客户拍板 → H2 升版 → 工程重新 accepted/baselined
→ 更新任务图、契约测试和追踪矩阵
```

工程层不得通过修改代码范围代替 CP。

### 技术契约变化（CC）

接口、数据结构或模块边界不成立时：

- 不影响业务需求、费用和验收：工程层按 CC/ADR 处理。
- 影响需求、费用、工期或验收：升级给经营层走 CP，不得把商业变更伪装成纯技术调整。

### 验收发现问题

- 既有功能做错：是工程缺陷，回工程修复，不自动扩大商业范围。
- 要求新能力：是需求变更，回经营层走 CP。
- 新发现的数据丢失、安全问题或严重缺陷：即使在原验收集之外，也必须定级并阻断相应验收。

## 6. 交接前检查

- 第 7 步 `RESULT: PASS` 后没有遗留 `OVERALL: PENDING-MODEL-CHECK`。
- P0/P1/P2 映射无遗漏，P0 均有报价和验收用例。
- F/A 编号转换无重复、无悬空，业务 ID 全程一致。
- `source` 可读、哈希可复算，工程层已明确接受或退回原因。
- 真实客户材料只在受控项目内交接，不进入公开规则库。
