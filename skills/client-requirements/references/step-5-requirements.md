# 第 5 步 · 需求条目

> 产物: `.req/requirements.md` ｜ 过关: `gate.mjs check 5`

## 陪跑流程

1. 用 ① 从 To-Be 的【改】【新增】步骤拆出需求，一个需求一个 `### F01` 小节。
2. 每条需求用 VDF 口径写：谁在什么场景用（V）、真实输入输出样例（D）、操作流程和失败处理（F）。
3. **验收必须可判定**：数字、能/不能、对照真实单据。客户说"要快"，追问"多快算快"。
4. AI 类需求额外填四项：资料来源、效果指标（带数字）、兜底（答不上或答错怎么办）、审核（谁审、审什么）。
5. 写「边界」：至少 3 条这次故意不做的。
6. `gate check 5`。

## Prompt ① To-Be → 需求条目

```
基于目标流程：<<注入 .req/process.md>>
问题答案：<<注入 .req/questions.md>>
真实材料：<<注入 .req/intake.md 的「真实材料」段>>
把 To-Be 中标【改】【新增】的每一步拆成需求，按 .req/requirements.md 的 ### F01 块格式输出。要求：
1. 来源写清：process 第几步 / 哪位角色原话 / 哪个 Q 编号。
2. 输入、输出样例用客户真实材料里的数据，不许用 {占位符}，不许编数据。
3. 验收写成别人能照着测的句子，带数字或明确的能/不能。
4. 优先级：没有它项目就不成立的才是 P0，P0 尽量不超过总数的一半。
5. AI 类需求把资料来源、效果指标、兜底、审核四项填全，效果指标要有数字。
凡是只能猜的地方用【需要确认】标出，不要替客户拍板。
```

## 验收写法对照

- 不可判定：查询速度要快 → 可判定：1 万条记录内，按订单号查询 2 秒内出结果
- 不可判定：报表要准确 → 可判定：用 9 月真实数据生成的月报，和财务手工表逐行对照，差异为 0
- 不可判定：知识库回答要智能 → 可判定：用客户提供的 50 个真实问题测试，40 个以上答案被客服主管判为可直接使用；答不上时回复"已转人工"

## 判据

- 至少 1 条需求，每条有优先级（P0/P1/P2）、来源、输入样例、输出样例、验收。
- 样例里没有 `{占位符}`。
- P0 的验收含数字或"能/不能"类判定词，不能只是"好用、稳定、快速"。
- AI 类需求四项齐全，效果指标含数字。
- 边界 ≥3 条。
- 模判：样例是否是客户的真实数据；需求是否都能追溯到 To-Be 的某一步。

## 过关前自查

- 有没有一条需求，来源写不出来？那是你加的，删掉或转成问题。
- 非功能需求填了吗？用户数、数据量、要不要内网部署，都影响架构和报价。
